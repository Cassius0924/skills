# PRD 大白话讲解

使用本 skill 时，要把 PRD 解释成“一个 PM 正在给工程、设计、运营或新同学讲需求”的样子。目标不是把原文压缩成信息点，而是帮助读者一步一步建立上下文：先知道原本有什么，再知道为什么出问题，最后理解这次方案到底在解决什么。

## 输出结构

输出 Markdown。开头直接进入讲解。

每个阶段使用下面的结构：

```md
**1. [阶段标题]**

一句话总结：[用一句话概括这个阶段的重点]

[大白话详细解释。先建立读者熟悉的对象、流程或用户行为，再解释冲突、变化或产品决策。]
```

阶段讲解结束后，用下面的结构收尾：

```md
**最后总结**

[简短总结这个需求本质上在做什么，以及为什么重要。]

**一句话总结版本：**

[用一句话概括整个 PRD 的本质。]
```

## 默认流程

先抽取，再讲解，不要一上来就复述原文。

1. 从文档里找出“原本有什么”：现有功能、现有流程、当前人工处理方式、当前权限或当前用户行为。
2. 找出“为什么要做”：业务收益、体验问题、效率问题、治理风险、合规风险、成本问题或规模化问题。
3. 找出“这次改什么”：新增入口、状态、规则、页面、流程、权限、审核、通知、后台能力或系统判断。
4. 找出“怎么控制”：准入、准出、封禁、冻结、回滚、审计、人工复核、通知、协议或异常处理。
5. 再把这些信息组织成阶段式讲解：先讲读者熟悉的旧世界，再讲问题，最后讲新机制。

## 讲解层次

按层次搭建读者理解：

1. 先从现有的用户侧功能、业务流程、权限、页面、角色或操作机制讲起。
2. 解释它在正常情况下原本是怎么工作的。
3. 解释是什么特殊业务场景、用户行为或运营诉求催生了这个需求。
4. 解释当前处理方式的问题：可能是效率低、风险高、体验差、成本高、收入损失或不可规模化。
5. 解释为什么团队不能简单地忽略、完全禁止或完全放开这件事。
6. 解释 PRD 提出的新产品机制。
7. 解释谁能用、在什么条件下能用、用户侧会看到什么状态变化。
8. 如果文档里有审核、通知、准入、准出、封禁、冻结、回滚、审计等控制机制，要讲清楚这些机制为什么存在。
9. 最后点明需求本质，例如：“把人工例外处理变成线上可控流程”“把分散的线下操作产品化成可追踪机制”“把低风险场景从人工判断升级为系统自动判断”。

优先使用因果表达：

- “因为现在会发生 X，所以 Y 变成了问题。”
- “团队不能直接做 A，因为会带来 B。”
- “所以这个 PRD 实际上是在把 C 改造成 D。”
- “从用户视角看，这意味着……”
- “从平台/团队视角看，这意味着……”

## 写作规则

- 使用用户的语言回答。用户用中文提问或 PRD 是中文时，输出中文。
- 可以写得大白话，但结构要专业，不要变成口水话。
- 阶段标题要具体，尽量避免只写“背景”“方案”“收益”这类泛标题。
- 每个主要阶段都要先写“**一句话总结：**”，再写详细解释。
- 要讲清楚“原来是什么”“这次变了什么”“为什么这件事重要”。
- 描述步骤、规则、角色、状态时可以使用编号列表。
- PRD 里的数字、门槛、角色、状态、处罚等信息，如果是理解机制的关键，就保留；如果只是旁枝信息，可以压缩。
- 原文标注 TBD、待定或信息缺失时，要如实说明，不要补编。
- 不要超过文档证据进行断言。可以使用“文档里的意思是”“可以理解为”“这里更像是在做”这类表达。

## 常见误区

- 不要把 PRD 的目录、标题或功能点列表直接改写成总结；读者要先理解“为什么有这个需求”。
- 不要一开始就讲页面、接口、字段、埋点等实现细节；先讲用户、业务或平台原本是怎么运转的。
- 不要把风险控制放到最后随便带过。如果准入、准出、封禁、冻结、审核是需求成立的关键，就要把它讲成主线的一部分。
- 不要为了“大白话”而加入原文没有的业务动机、数字、人物或因果关系。

## 推荐段落顺序

根据文档复杂度调整段落数量。一个常见 PRD 可以按下面的节奏讲：

```md
**1. 先说原本有什么**

一句话总结：先把读者拉到一个熟悉的现有功能或流程上。

...

**2. 这个现有功能在特殊场景下遇到了什么问题**

一句话总结：说明需求不是凭空来的，而是某个真实场景把原流程顶住了。

...

**3. 现在是怎么临时处理的**

一句话总结：解释当前绕路方案或人工方案为什么能救急但不能长期用。

...

**4. 所以这次 PRD 要做什么**

一句话总结：把需求的核心动作翻译成一句产品机制变化。

...

**5. 谁能用、怎么用、什么时候生效**

一句话总结：讲清楚准入、操作路径和用户可感知的变化。

...

**6. 后续怎么退出、限制或治理**

一句话总结：讲清楚这个能力不是无条件放开，而是有生命周期和风险控制。

...

**最后总结**

...

**一句话总结版本：**

...
```

## 虚构示例

输入背景：

> 一份 PRD 说：某内部客服工具现在允许高级客服在客诉升级后手动发放补偿券。业务希望为符合条件的小商家增加一个自助申请补偿券的入口。资格判断基于账号注册时长、近期投诉率和月订单量。系统要自动通过低风险申请，拒绝不符合条件的申请，给用户发送通知，并允许风控运营在发现滥用时冻结该能力。

好的输出风格：

```md
**1. 先说原本有什么：客服后台可以人工发补偿券**

一句话总结：这个能力原本是客服在处理客诉升级时使用的人工补偿工具。

可以理解成，商家遇到一些特殊售后问题后，如果普通流程处理不了，会升级到客服。客服确认情况后，可以在后台给商家发一张补偿券，用来安抚商家或补偿损失。

这个能力本身不是给商家直接使用的，而是客服判断后人工操作。

**2. 为什么现在要改：人工发券扛不住高频小额诉求**

一句话总结：一些低风险、规则明确的补偿场景，其实不需要每次都走人工客服。

现在的问题是，有些小商家的诉求很标准，比如账号正常、投诉率不高、订单量也达到一定规模，只是偶发遇到售后损失。每次都让客服人工判断，会让处理链路变长，也会消耗客服人力。

所以这个 PRD 不是要取消客服判断，而是把一部分规则明确的低风险场景，从人工处理变成线上自助申请。

**3. 这次具体要做什么：给符合条件的商家一个自助申请入口**

一句话总结：把原来客服后台里的人工补偿动作，前置成商家可见、系统可判断的申请流程。

商家会在对应页面看到补偿券申请入口。点击后，系统会检查商家是否符合条件，比如账号时间、近期投诉率、月订单量等。

如果符合条件，低风险请求可以自动通过；如果不符合条件，页面会直接告诉商家原因，而不是让商家反复找客服。

**4. 为什么还需要风控：自助能力不能无条件开放**

一句话总结：只要把人工权限开放给用户侧，就必须配套准入、通知和冻结机制。

如果没有限制，商家可能会频繁申请，甚至形成套利。所以系统除了自动校验，还需要让风控运营在发现异常时冻结商家的申请能力。

这样做的核心不是“多发券”，而是让低风险补偿更高效，同时把滥用风险控制住。

**最后总结**

这个 PRD 的本质，是把原来依赖客服人工判断的补偿券发放，拆出一部分低风险、规则明确的场景，做成商家可自助申请、系统可自动审核、风控可干预的线上流程。

**一句话总结版本：**

它是在把“客服人工发补偿券”产品化成一套“商家自助申请 + 系统自动判断 + 风控兜底”的标准机制。
```

## 质量检查

输出前检查：

- 输出是 Markdown。
- 每个主要阶段都有一句话总结。
- 讲解从“原本有什么”开始，而不是直接讲实现细节。
- 不熟悉业务的人也能看懂为什么要做这个需求。
- 最后总结讲的是需求本质，不只是功能清单。
- 一句话总结版本足够短，可以被复用到汇报或对齐文档里。
